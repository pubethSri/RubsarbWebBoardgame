# Rubsarb Concurrency & Synchronization Architecture
# Context: Fixing Race Conditions & "Drag Kill" bugs in Bun + Svelte 5

## 1. The Core Philosophy: "Intents, Not Snapshots"

**The Root Cause:**
The current system uses a "Snapshot" model where clients send the full array (`this.board = payload.board`). This causes:
1.  **Race Conditions:** If two players move cards simultaneously, the last request overwrites the first, causing cards to vanish.
2.  **Drag Kill:** If an update arrives while a player is dragging, the UI forces a re-render, canceling the drag operation.

**The Solution:**
We switch to **Server Authority** using **Atomic Commands**.
- Clients send **Intents** ("Move Card X to Index Y").
- Server calculates the **Result**.
- Clients implement **Update Buffering** to protect the drag state.

---

## 2. The Protocol Redesign

### A. Client-to-Server (The Request)
Payloads must be lightweight and reference IDs, not full objects.

**Event:** `MOVE_CARD`
{
  "type": "MOVE_CARD",
  "payload": {
    "cardId": "uuid-of-card",
    "targetIndex": 2
  }
}

### B. Server-to-Client (The Broadcast)
The server broadcasts the state *after* processing the move.

**Event:** `BOARD_UPDATED`
{
  "type": "BOARD_UPDATED",
  "payload": {
    "board": [ ...full array of card objects... ],
    "lastMover": "PlayerName",
    "version": 105 // Incrementing integer to track sync order
  }
}

---

## 3. Server-Side Implementation (Bun/Elysia)

Since Javascript (Bun) is single-threaded, we don't need database locks for in-memory arrays. We just need to ensure the logic runs synchronously in the handler.

**Logic Flow for `MOVE_CARD`:**

1.  **Find**: Look up `cardId` in the current `room.board` array.
2.  **Validate**: 
    - Does the card exist?
    - Is the card "Locked" (already revealed)? -> Reject move.
    - If invalid, send `ERROR` to client and stop.
3.  **Execute (Atomic)**:
    - `board.splice(oldIndex, 1)` (Remove from old spot)
    - `board.splice(newIndex, 0, card)` (Insert at new spot)
    - `room.version++`
4.  **Broadcast**: Send the new board to **ALL** players (including the mover).

**Pseudo-Code (Server):**
app.ws('/ws', {
  message(ws, message) {
    const { type, payload } = JSON.parse(message);
    
    if (type === 'MOVE_CARD') {
      const room = getRoom(ws.data.roomId);
      const { cardId, targetIndex } = payload;
      
      // 1. Find current index
      const currentIndex = room.board.findIndex(c => c.id === cardId);
      
      if (currentIndex === -1) return; // Card missing/Error
      
      // 2. Atomic Move
      const [card] = room.board.splice(currentIndex, 1);
      room.board.splice(targetIndex, 0, card);
      room.version += 1;
      
      // 3. Sync Everyone
      server.publish(room.id, JSON.stringify({
        type: 'BOARD_UPDATED',
        payload: { board: room.board, version: room.version }
      }));
    }
  }
})

## 4. Frontend Implementation (Svelte 5 + Dnd-Action)

This addresses **Issue B: The "Drag Kill"**. 
We must separate the **Server State** from the **UI State** while dragging.

### The Strategy: "Update Buffering"

1.  **State variables:**
    - `localBoard`: The array bound to the UI (`items={localBoard}`).
    - `isDragging`: Boolean flag, managed by `dndzone` events.
    - `pendingServerUpdate`: Stores a server update if it arrives *while* you are dragging.

2.  **While Dragging (`isDragging = true`):**
    - If a `BOARD_UPDATED` event arrives from the server, **DO NOT** update `localBoard`.
    - Instead, save it to `pendingServerUpdate`.
    - **Why?** Updating `localBoard` mid-drag causes `svelte-dnd-action` to reset the DOM, killing the drag.

3.  **On Drop (`finalize`):**
    - Send `MOVE_CARD` to server.
    - Check `pendingServerUpdate`. If one exists, apply it now (or wait for the server to confirm your move and send a fresh update).

### Code Structure (Svelte 5)

<script lang="ts">
  import { dndzone } from 'svelte-dnd-action';
  
  let localBoard = $state([]);
  let isDragging = false;
  let pendingUpdate = null; // Buffer

  // WebSocket Handler
  socket.onmessage = (event) => {
    const msg = JSON.parse(event.data);
    
    if (msg.type === 'BOARD_UPDATED') {
      if (isDragging) {
        // 🛑 BUSY: Buffer the update, don't break the UI
        console.log("Update received while dragging. Buffering...");
        pendingUpdate = msg.payload.board;
      } else {
        // ✅ IDLE: Apply immediately
        localBoard = msg.payload.board;
      }
    }
  };

  // Drag Handlers
  function handleDndConsider(e) {
    isDragging = true;
    localBoard = e.detail.items; // Optimistic UI update
  }

  function handleDndFinalize(e) {
    isDragging = false;
    const items = e.detail.items;
    localBoard = items; // Final local visual state
    
    // 1. Identify what changed (Logic to find the moved card)
    // Note: You need a helper to find which item ID changed index
    const movedCard = findMovedCard(items); 
    
    if (movedCard) {
        // 2. Send Intent to Server
        socket.send(JSON.stringify({
            type: 'MOVE_CARD',
            payload: { cardId: movedCard.id, targetIndex: movedCard.index }
        }));
    }

    // 3. Process Buffered Updates (Reconciliation)
    if (pendingUpdate) {
        // We have a choice here: 
        // A. Apply pending immediately (might jump visuals)
        // B. Discard pending and wait for the response to our own MOVE_CARD (smoother)
        pendingUpdate = null;
    }
  }
</script>

<div use:dndzone={{items: localBoard}} 
     on:consider={handleDndConsider} 
     on:finalize={handleDndFinalize}>
   </div>

## 5. Migration Checklist for AI Agent

1.  **Refactor Server**: Remove `this.board = payload.board`. Replace with `splice` logic based on ID.
2.  **Refactor Client Send**: In `handleDndFinalize`, stop sending the whole array. Calculate the `toIndex` of the moved card and send `MOVE_CARD`.
3.  **Refactor Client Receive**: Add the `isDragging` check. If true, buffer the incoming WebSocket message into a variable, do not apply to state.
